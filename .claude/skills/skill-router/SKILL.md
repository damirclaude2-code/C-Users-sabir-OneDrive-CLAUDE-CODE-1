# Skill Router

Ты работаешь как слой маршрутизации навыков.

Твоя задача не выполнять вместо всех остальных навыков, а:

- распознать тип задачи;
- выбрать минимальный уместный маршрут;
- коротко назвать, какой режим работы включается и почему;
- не путать выбор навыка с оценкой сложности задачи.

## Когда использовать

Используй этот навык, когда:

- пользователь прямо просит применить навыки;
- неочевидно, какой режим нужен;
- задача состоит из нескольких фаз;
- перед стартом полезно коротко назвать рабочий маршрут.

## Trigger

Подключай `skill-router`, если в задаче есть сигналы:

- "use skills";
- "примени навыки";
- "автовыбор навыков";
- "какой навык лучше";
- "подключи нужный режим";
- "с каким skill лучше это делать";
- "выбери режим работы сам".

## Навыки и режимы, которые ты должен различать

1. `auto-prompt-upgrade`
   - когда задача сырая, размытая или задана слишком общо.

2. `copywriter`
   - когда главный результат - текст.

3. `designer`
   - когда нужно улучшить существующую визуальную подачу.

4. `design-elements-pack`
   - когда нужно быстро собрать структуру из типовых сильных блоков.

5. `fact-checking`
   - когда важна проверка фактов, цифр, обещаний и свежести.
   - **⚠ статус в этом проекте: source-of-truth файл `06-fact-checking-skill-4-4.md`
     не был передан при установке, поэтому сам навык `fact-checking` физически
     не установлен. Этот пункт маршрутизации оставлен для полноты картины, но
     реально подключить `fact-checking` пока нельзя — см. `CLAUDE.md`.**

6. `search-and-read-web`
   - когда задача зависит от реальных внешних источников, сайтов или свежих данных.

7. `design-style-policy`
   - когда задача про дизайн и нужно понять, использовать ли default
     `design-elements-pack` baseline или уважить явный запрос на другой стиль.

8. `web-design-libraries-setup`
   - когда проект вебовый и нужно установить или аккуратно встроить
     `shadcn/ui` и `daisyUI`.

## Главное различие, которое нельзя путать

- `designer` = улучшить уже существующий визуальный артефакт;
- `design-elements-pack` = собрать каркас из сильных паттернов;
- `fact-checking` = проверить claims;
- `search-and-read-web` = найти и прочитать внешние источники;
- `design-style-policy` = default baseline включен, но user override важнее;
- `web-design-libraries-setup` = ставим web libraries, если style-risk низкий,
  или делаем uplift plan, если есть существующая дизайн-система;
- `auto-prompt-upgrade` = сначала сделать постановку задачи сильнее.

## Sequence Canon

1. Сначала проверь качество входного запроса.

   Если задача сырая, двусмысленная или слишком общая, первым ходом выбирай
   `auto-prompt-upgrade`.

2. Определи главный тип работы.

   Спроси себя:

   - это текст;
   - дизайн;
   - набор готовых блоков;
   - факт-проверка;
   - web research;
   - комбинация из двух фаз?

3. Если нужен web research, ставь его раньше copy/fact work.

   Правильная логика:

   - сначала найти и прочитать;
   - потом проверять или писать.

4. Выбирай минимальный маршрут.

   Обычно хватает:

   - одного навыка;
   - или короткой цепочки из 2-3 шагов.

   Не строй длинные цепочки без явной причины.

5. Если задача про дизайн, проверь style direction.

   По умолчанию используй `design-elements-pack` baseline.

   Если пользователь явно сказал:

   - "не используй design-elements-pack";
   - "не используй загруженный дизайн-стиль";
   - "не опирайся на shadcn/daisyUI";
   - "подбери другой визуальный стиль";
   - "используй мой референс вместо библиотеки";

   тогда уважай override и не навязывай bundled style.

   Вопрос нужно задавать только если требуется code-level установка
   web-библиотек или если пользователь отключил baseline, но не дал нового
   direction.

   Для установки web libraries используй правило:

   - web project + no existing design system -> install `shadcn/ui` и `daisyUI`;
   - web project + existing design system -> uplift plan и подтверждение;
   - non-web project -> не ставить npm libraries.

6. Перед неочевидной или составной задачей коротко назови маршрут.

   Используй формат:

   - `Тип задачи`
   - `Какой навык подключаю`
   - `Почему`
   - `Что сделаю дальше`

7. Не подменяй triage.

   Если в проекте позже появится `agentic triage`, он будет стоять выше.
   Тогда triage отвечает на вопрос "насколько задача сложная и рискованная",
   а router - "какой навык подключить".

## Типовые маршруты

### Сырой запрос на текст

`auto-prompt-upgrade -> copywriter`

### Текст с фактами и цифрами

`fact-checking -> copywriter` (в этом проекте `fact-checking` пока не
установлен — см. предупреждение выше; временно можно проверять факты вручную
или через `search-and-read-web`)

### Свежий рыночный материал

`search-and-read-web -> fact-checking -> copywriter` (аналогично: шаг
`fact-checking` недоступен, пока не будет добавлен source-of-truth файл)

### Существующий слайд или экран

`designer`

### Новый лендинг или слайд с нуля

`design-elements-pack -> designer`

### Новый веб-экран в совместимом репо

`design-elements-pack -> designer`

Если нужна code-level установка web UI libraries:

`design-elements-pack -> web-design-libraries-setup -> designer`

## Anti-Patterns

- делать вид, что один навык подходит для всего;
- выбирать цепочку длиннее, чем нужно;
- путать `designer` и `design-elements-pack`;
- пытаться подключать web UI libraries для презентаций и не-вебовых задач;
- пропускать style-risk check перед установкой web libraries;
- игнорировать явную просьбу пользователя не использовать bundled style;
- ставить `copywriter` раньше фактов там, где доказательства ещё не проверены;
- начинать работу, не назвав маршрут в действительно неочевидной задаче;
- превращать router в triage-движок или в исполнителя вместо других навыков;
- делать вид, что `fact-checking` подключён, если он не установлен в проекте.

## Качество результата

Считай результат хорошим только если:

- тип задачи распознан правильно;
- выбран минимальный уместный маршрут;
- отличие между похожими навыками объяснено верно;
- пользователь понимает, почему выбран именно этот путь;
- ты не усложнил задачу лишними режимами.

## Быстрая проверка перед отдачей

Перед финалом проверь:

- Это точно тот навык, который делает основную работу?
- Нужна ли здесь внешняя проверка раньше writing/design шага?
- Не перепутал ли я аудит с конструктором блоков?
- Можно ли сократить маршрут на один шаг без потери качества?

Если можно, сокращай.

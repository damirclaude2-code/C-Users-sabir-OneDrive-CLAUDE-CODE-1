# Design Elements Pack

Ты работаешь как default structural design pack для Claude Code.

Если пользователь не попросил явно другой стиль, этот pack является базовым
visual baseline для задач про дизайн.

Твоя задача - не просто "дать совет по дизайну", а дать опору, из которой можно
собрать внятный, спокойный и сильный артефакт:

- страницу;
- экран;
- слайд;
- comparison block;
- pricing section;
- proof section;
- CTA block.

## Когда использовать

Используй этот pack по умолчанию, когда:

- артефакт еще не собран;
- нужно быстро выбрать сильные блоки;
- не хочется стартовать с пустого листа;
- нужно перевести идею в skeleton;
- нужно собрать каркас страницы, экрана или слайда;
- нужен более системный visual baseline без платных kits.

Также используй его по умолчанию для:

- веб-страниц;
- UI-экранов;
- презентаций;
- учебных слайдов;
- схем и visual explainers.

Если визуальный артефакт уже существует и его надо улучшать, сначала чаще нужен
`designer`, а не этот pack.

Но даже при работе через `designer` visual baseline из этого pack можно
использовать как стиль по умолчанию.

## Override

Не используй bundled baseline, если пользователь явно просит:

- "не используй design-elements-pack";
- "не используй загруженный дизайн-стиль";
- "не опирайся на shadcn/daisyUI";
- "подбери другой визуальный стиль";
- "используй мой референс вместо библиотеки";
- "сделай в другом стиле".

В этом случае:

1. уважай override;
2. коротко назови, что меняешь visual direction;
3. всё равно сохраняй базовые принципы качества:
   - иерархия;
   - читаемость;
   - отсутствие AI slop;
   - аккуратная структура.

## Trigger

Подключай `design-elements-pack`, если в запросе есть сигналы:

- "собери структуру";
- "какие блоки нужны";
- "с чего начать";
- "дай сильный skeleton";
- "нужен hero / pricing / FAQ / comparison / CTA";
- "не хочу придумывать с нуля";
- "собери landing / slide / page structure".

## Что этот pack чинит

- пустой старт;
- хаотичный набор секций;
- бессистемные UI-блоки;
- generic AI layout;
- страницы без логики маршрута;
- слайды, где блоки набросаны без драматургии;
- отсутствие визуального baseline.

## Как работать

1. Сначала открой:

- `references/pattern-selection.md`
- `references/pattern-catalog.md`
- `references/presentation-rules.md` при задачах про слайды

2. Определи:

- тип артефакта;
- цель;
- уровень тепла аудитории;
- что должно произойти после просмотра.

3. Затем открой:

- `references/visual-rules.md`
- `references/style-override-policy.md`

И собери маршрут так, чтобы он не превращался в шумный marketing sludge.

4. После этого выбери один из skeletons в `templates/` как базовую форму.

5. Если проект вебовый и реально использует компонентный стек, открой:

- `references/open-source-stack.md`

И по умолчанию опирайся на бесплатные источники паттернов, а не на платные UI
kits.

6. Если задача про презентацию или учебный слайд, не тащи web UI libraries.

В этом случае работай через:

- structural patterns;
- `references/presentation-rules.md`;
- presentation skeleton templates.

## Sequence Canon

1. Определи тип артефакта:

- cold landing;
- warm landing;
- pricing page;
- comparison page;
- sales slide;
- explanatory slide;
- dashboard explainer;
- feature section.

2. Определи главную задачу:

- объяснить;
- продать;
- сравнить;
- доказать;
- снять возражения;
- довести до выбора;
- довести до действия.

3. Выбери минимальный сильный маршрут блоков.

Не перечисляй 12 секций без причины. Почти всегда лучше:

- один основной маршрут;
- максимум одна альтернатива.

4. Подбери skeleton из `templates/`.

5. Проверь решение по `references/visual-rules.md`.

6. Если нужен более конкретный компонентный ориентир, используй бесплатный
   open-source baseline из `references/open-source-stack.md`.

7. Если это presentation task, используй skeleton из `templates/` для слайда, а
   не web component route.

## Anti-Patterns

- собирать структуру как случайный список секций;
- давать 8 вариантов вместо одного сильного;
- лечить отсутствие логики декоративностью;
- ставить pricing, FAQ или testimonials "потому что так делают все";
- использовать Tailwind Plus или другие paid kits как дефолтный ответ;
- тащить `shadcn/ui` или `daisyUI` в presentation workflow;
- игнорировать явный user override на другой стиль;
- путать этот pack с детальным дизайн-аудитом существующего экрана.

## Качество результата

Считай результат хорошим только если:

- маршрут блоков логичен;
- каждый блок решает отдельную задачу;
- артефакт не выглядит как generic AI page;
- Claude может быстро перейти от идеи к структуре;
- решение опирается на бесплатные и повторяемые источники;
- после ответа понятно, какой skeleton брать за основу.
- если пользователь попросил другой стиль, bundled baseline не навязан поверх
  его запроса.

## Быстрая проверка перед отдачей

- Какой это тип артефакта?
- Какова одна главная цель?
- Почему именно этот порядок блоков?
- Можно ли убрать 1-2 блока и сделать чище?
- Не выдал ли я случайный набор секций вместо маршрута?

Если да, пересобери.
